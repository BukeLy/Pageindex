# Metadata Query

## Schema First

`get_metadata_schema` is the tool that tells the LLM which fields exist and
what types they have. The MCP instructions explicitly tell the model to call it
before building a metadata filter.

This is the right pattern for LLM-driven retrieval:

```text
schema -> validated query DSL -> backend execution
```

not:

```text
schema -> raw SQL generated by the LLM
```

## `search_documents(mode="metadata")`

Metadata query mode accepts:

```json
{
  "mode": "metadata",
  "recursive": true,
  "metadata": {
    "metadata_filter": {"year": {"$gte": 2024}},
    "sort": {"year": -1},
    "aggregates": {"n": {"$count": {}}},
    "group_by": ["category"]
  }
}
```

The nested `metadata` object is required by the MCP schema.

## Query Modes

`search_documents` has two modes:

- `query`: keyword precision search over file name and description.
- `metadata`: structured backend query over metadata.

`browse_documents(sort="relevance")` remains the semantic recall path.

## Group By

The MCP schema caps `group_by` at 3 fields, while backend code uses a max of 5.
The final FileSystem API should choose one contract and make all clients share
it.

## Design Takeaway

The model-facing guidance is strong. The long-term system should formalize this
as a `FileSystemQuery` AST and keep MCP as one client of that AST.
